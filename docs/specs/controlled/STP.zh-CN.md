# 软件测试计划

[English](STP.md) · 中文

本仓测什么、怎么测、哪些留给另一个仓。`SRS.md` 说包必须做什么，`SDD.md`
说怎么搭，本计划说每一条断言怎么被检查出来。

## 范围

纳入：`packs/` 下的包——它们的外部清单、数据、构建出的归档，以及装进引擎后
一个人看到的东西。

不纳入：引擎本身。回合顺序、存档格式、层合并、菜单都是引擎的行为，有它自己
在 `lethebar` 的测试套件。这里的用例可以说「装进引擎看一眼」，但不断言引擎
代码。

## 层级

| 层级 | 回答的问题 | 怎么跑 |
| --- | --- | --- |
| 静态 | 归档是不是引擎接受的形状 | 对构建出的 zip 跑 `check_pack.py` |
| 数据 | JSON 里的数字与 SRS 是否一致 | 读文件，比字段 |
| 构建 | 两个人会不会得到同样的字节 | 构建两次，比 sha256 |
| 安装 | 引擎收不收这个包 | 由人安装 |
| 试玩 | 玩起来是否符合 SRS | 由人推进回合 |

前三级是机械的，任何拿了本仓的人都能重跑；后两级由人做并留下截图——这是有意的：
引擎的套件证明引擎在跑，不证明这个包讲了它宣称的那个故事。

## 环境

- 引擎：批次记录里写明的那个提交，用 Godot 4.7.2 或引擎自带的网页构建。
- 构建：Python 3.14，仓库检出在批次的基提交上。
- 安装：浏览器里引擎的「从 zip 安装」界面，或桌面版的包列表。

## 进入与退出

用例只在包的字节为这批冻结之后才跑——跑的是将要发出去的那次构建，不是工作树。
用例通过的标准是 `STD.md` 里那一行的判据成立，证据是留在批次目录里的命令输出
或留在记录里的截图。

整套跑完的条件是：`SRS.md` 里每条 `REQ-` 至少被一个用例覆盖，且没有用例留
`TBD`。覆盖是查出来的，不是声明的：`check_verification.py`。

## 测试区域

| 区域 | 前缀 | 覆盖 |
| --- | --- | --- |
| 身份 | `TC-IDN-` | 存档与货架依赖的清单字段 |
| 进程 | `TC-RUN-` | 回合、段位、结束条件 |
| 资源 | `TC-RES-` | 初值、上下界、行动、声望规则、关系 |
| 叙事 | `TC-NAR-` | 入口节点、内容块、meta、世界归属、翻译 |
| 打包 | `TC-PKG-` | 素材、封套、能力、引擎区间、可复现 |
| 安装 | `TC-INS-` | 人把归档装进引擎 |
| 试玩 | `TC-PLY-` | 人推进回合，数字按规格变化 |
| 层 | `TC-LAY-` | 层归档保持同一封套并声明目标 |
| 发布 | `TC-REL-` | 发出去的资产就是构建出的资产 |

## 有意不测的

- 引擎的回合顺序、存档格式、层合并语义——那是 `lethebar` 的套件，在这里重复
  等于测另一个仓。
- 本地化的渲染、字体、排版——引擎负责画，用例只检查字符串存在。
- 封套之外的负载与体积——`check_pack.py` 已按引擎的上限执行，用例不测计时。

## 追溯

`SDD.md` 为每条需求点名承载它的文件；`STD.md` 为每个用例点名它覆盖的需求与
重跑方式。批次的出口记录引用它跑过的用例；基线冻结文档，不冻结运行。
